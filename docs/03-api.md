# 03 · API

Two surfaces:

1. **Edge Functions** — the action endpoints (create a task, health). REST-ish, JWT-required
   (except `health`). The full contract is in [`openapi.yaml`](openapi.yaml).
2. **PostgREST + Realtime** (auto-generated by Supabase) — reads of `tasks`, `artifacts`,
   `task_events`, `skills`, all constrained by RLS, plus the Realtime subscription that powers
   the Studio timeline. The client uses `supabase-js`; there is no hand-written read API.

This hybrid follows the original API plan's intent (REST for sync operations, an async
channel for progress) while replacing the bespoke WebSocket with Supabase Realtime.

## Resources

| Resource | Access | Notes |
| --- | --- | --- |
| `tasks` | create via `create-task` fn; read/list/soft-delete via PostgREST (RLS) | central resource; ownership-scoped. |
| `artifacts` | read via PostgREST (RLS); bytes via signed URL | 4 per creative task. |
| `task_events` | read + Realtime subscribe (RLS) | append-only timeline. |
| `skills` (agents) | read via PostgREST | informational registry; writes are ADMIN/service_role. |
| `auth` | Supabase Auth (`supabase-js`) | OAuth2/OIDC + JWT, PKCE. |

## Conventions (from the API plan)

- **Async create.** `POST` create-task returns `{ task_id, status: "queued" }` fast; progress
  arrives over Realtime. No long-held connections.
- **Soft delete.** Deleting a task sets `deleted_at`; rows are filtered out by RLS and a
  cleanup job hard-deletes after the retention window.
- **Generic 404.** Unauthorized / non-existent rows are indistinguishable to the caller (RLS
  makes them simply "not found"), preventing user/resource enumeration.
- **Tiers & rate limits.** `tier` (S/M/L) is a request preference resolved by the router.
  Basic per-user/per-tier rate limiting lives in `create-task`; gateway-grade limiting is
  scale-vision.
- **Error shape.** `{ error: { code, message, details?, request_id } }`. `request_id` equals
  the task `trace_id` where applicable, for log correlation.

## Realtime contract

Subscribe to `task_events` filtered by `task_id`. Event `type` values, in order:
`task_created → routing_done → variation_ready (×4) → validation_done → delivered`
(or `failed` with an `error` payload at any stage). The UI must tolerate out-of-order or
missed messages and **fall back to polling `task_events`** if Realtime drops a message.
